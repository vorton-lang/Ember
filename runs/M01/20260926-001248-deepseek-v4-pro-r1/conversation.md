## 方案一：「严格 Hylo 派」——概念极简，一切靠推断

完整采用 MVS（mutable value semantics）：类型系统纯粹值语义，参数按 `let / inout / sink` 三模式传递。没有 GC、没有生命周期标注、可变别名在类型层面不存在。

- ✅ 数据竞争在编译期不可能发生；值语义让缓存行为可预测（贴着你的 roofline 思维）
- ✅ 概念总数最少，一门「逻辑上很干净」的语言
- ❌ 图结构、循环引用、缓存必须绕行（显式 box 或索引池）；学术路线参考实现少，卡住了没人带路
- ❌ 概念墙与你的「上手试→卡住查」学习模式有冲突

## 方案二：「工程务实派」——Swift 式外围 + 推断内核

所有权推断做内核，外围包工程便利：引用类型（ARC）兜底图结构和 UI 树、协议扩展、成熟模块系统、REPL。相当于「Swift 把 ARC 换成所有权推断」的假想版本。

- ✅ 真实项目都写得动：游戏对象图、UI 树、缓存不用绕行
- ✅ 工程体验好，跨平台有大量可参照的成熟设计
- ❌ 两套内存语义（值/引用）边界要人判断；引用计数的运行时开销让性能不完全可预测
- ❌ 语言更复杂，与你「激进简洁」的审美有张力

## 方案三：「验证派」——你的项目史就是需求文档 ⭐ 我的推荐

不从语言理论出发，从你踩过的坑出发。内核同样是严格所有权推断，但每个外围特性都对应你项目里的一个真实痛点：

| 特性 | 出处 |
|---|---|
| 状态可序列化是一等公民，纯逻辑域自动可存档 | Ring-rs 存档系统 |
| derive 式自动生成：序列化/比较/hash 不手写 | Rust 经验 |
| 内建属性测试 + 变异测试 | cargo mutants 偏好 |
| 错误信息带定位 + 修复建议 | 「>3 轮不可接受」 |
| 0.x 无兼容包袱、破坏性变更直接改的演进哲学 | Ring-rs 反馈记录 |
| 单一编译器：增量 <200ms + REPL 复用同一套 | 你的反馈循环选择 |

- ✅ 每个特性都有你的真实项目背书，不是空想设计；交付感强
- ✅ 内核保持方案一的严格性，外围做减法而不是加法
- ❌ 特性来源杂，需要设计者自律，否则会变成大杂烩

**我的推荐**：方案三为骨架、方案一为内核、方案二按需取经——图结构问题用 Swift 的解决思路（显式引用池）但不引入 ARC，保住性能可预测性。
