# Manager 的 hold-out 案例（2026-10-18）

[Lobotomy](https://github.com/vorton-lang/Lobotomy) 的 Angela 提示词按真实使用中的失败迭代，这些失败作为 hold-out 案例：它们没有用来调过提示词，用来检验新版本。第三轮面试的结论里写了"下一轮要换新案例"，这一批就是新案例。

## 来源

- 素材是本机 Claude Code 在 Lobotomy 项目上的 19 个会话，时间从 2026-10-01 到 10-18。会话中 Claude Code（Opus 5.5）同时担任开发者和项目经理，做的正是 Angela 将来要做的事。
- 用户本人的 302 轮话，由 Claude 子 agent 按一份编码表逐轮标注。用户抽查了 24 条样本，没有发现标错的。标出的纠正与重述共 44 个。
- 其中 4 个与 Angela 无关（只关乎这个仓库的合并或工程细节），4 个和第一轮重复（第一轮的 case-01、05、06、07），都不收。剩下 36 个。
- 每个案例由一个 Claude 子 agent 从原始会话写成，格式同第一轮的 `cases/`。截断点放在助手出错的那次回应之前，也就是它当时在回应的那条用户消息。

## 类别

类别是助手当时的失败模式，分类由 Claude 做：

| 类别 | 案例数 |
|---|---|
| 1 没对齐就动手，或者做多了 | 8 |
| 2 已有的决定或记录，在做决定的那一刻没用上 | 8 |
| 3 误读用户的话 | 7 |
| 4 取舍偏离用户的价值 | 6 |
| 5 项目经理的功课没做 | 2 |
| 6 形式、语言与读者 | 5 |

## 用法

- 和第一轮一样，发给候选的只有"历史"和"截断处的用户消息"。"来源""之后实际发生了什么""选这个点的理由"三节只给评审者看。第一轮 `interview.mjs` 的 `caseInput` 按这三个标题去掉它们。
- 同一会话中，编号大的案例的历史可能包含编号小的案例的结果。同一个候选做这些案例时，每个案例单独开会话。
- 有两对案例截断在同一条消息上，纠正的是同一次回应里的两处：case-30 和 case-31，case-33 和 case-35。

## 处理与限制

- **case-04、05、06 不是干净的 hold-out。** 它们的失败和用户的纠正，原样出现在第一轮案例的历史里：case-04 在第一轮 case-05 的历史中，case-05 在第一轮 case-07 中，case-06 在第一轮 case-08 中。初稿 v1 是对着第一轮的案例改的。检验新提示词时，可以把它们当回归案例，不计入 hold-out 的结果。
- **隐私。** 用户在会话中自己说的话原样收录，与第一轮相同。用户与 Dot 的私有对话记录不收录原文，只写一句中性的概述。本地草稿不收录大段原文。凭据、私钥位置和别人的账号都不收录。
- **有些"当时可读到的记录"是助手在出错的那次回应中才读到的**，案例中都标了读取时间：case-10、19、24、30、31、32、33、34、36。不放进来，候选就看不到当时的事实，例如 case-24 中 PR 的体量。
- **有几个案例的截断消息和出错的内容关系不大。** 出错的回应是后台通知触发的，截断只能放在之前最后一条用户消息上，历史末尾用一两句话交代后来到达的通知：case-08、13、16、19。
- **位置不同。** 这些失败发生在助手同时写代码、做判断的时候；Angela 不写代码。评审时看判断和交给下层的方式，不看执行。
- **都由 Claude 整理。** 标注、分类和案例文件都出自 Claude 子 agent，案例文件没有经过人工逐条审阅。机械核对（`verify.mjs`，不在本目录）确认了每个截断消息都能在对应会话中原样找到，来源与清单一致，没有凭据和邮箱。
