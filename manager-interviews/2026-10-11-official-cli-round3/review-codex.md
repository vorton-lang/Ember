**2．逐案简评：只列变化**

- **case-01：移除了一个自相矛盾，但没有明显提升接入方向的判断。**  
  甲 v0 一边提醒不能把沉默当接受，一边准备将未回应的 HCI 设计“作为默认设计带上”；v1 删除了这个动作。另一方面，v1 说多 harness 要求推翻了“直连 Claude Code、暂不引入 ACP”的建议，混淆了两件事：单 harness 范围需要修改，并不意味着直接调用或不采用 ACP 就被否定。  
  乙 v0 至少给出“薄自建抽象”的推荐，v1 退到调查后再提出 adapter 建议，下一步稍欠具体。两者仍保留 SDK 调查，不能据此直接判定失败：截断处尚不足以证明用户排除了所有 SDK，更不能从用户动机推出合规结论。可改进的是先给官方 CLI 路线的具体草案，再标出会改变它的未知点。

- **case-02：限定词处理有所加强，甲仍有“先说未定、随后落定”的张力。**  
  乙 v1 明确指出不能把“倾向”当成定案，比 v0 更准确。甲 v1 加入了解读不能增加下层权限，也更注意用户跳过了向上议题；但随后说“把这一条按‘默认做法’落定”，并加入来源标签和异议直达规则。它们可以成为建议，不能仅凭这句话作为用户已接受的规则。甲还扩大了向上的讨论内容，未使回应更省力。

- **case-03：甲修正了续跑条件和擅自延期，又增加了不必要的功能决策。**  
  v1 明确写出“排队 → 中断 → 用户点继续 → 新 turn”，消除了 v0“马上看到”与手动继续之间的含混，也不再擅自把第4轮留到明天。可是它刚建议快捷操作不进 M1，下一句就请用户决定是否在 M1 正式提供，增加了一次本可避免的范围讨论。  
  这里无需预知用户之后会要求“只记录”。能够解释现有路径、记录未验证条件，并继续第4轮，就已经是低成本的纠正方式。

- **case-04：限定词和一致性检查更好，关键后果仍未提前。**  
  甲 v1 更清楚地保留“先”的临时性质；面试3也增加了遇到一般 failed 路径未定义时停下回报的要求。但它已明确发现“其他 role 照常启动”可能违反用户理由，仍安排发布后报告。这不是缺少另一种读法，而是读出来之后没有改变动作顺序。新增 `ideas.md` 待办也不是必需：暂时撤掉一条规则，不自动意味着要另立未来功能条目。  
  乙取消了 TL 直接向 Worker 交接，但仍派两者，且没有补上同域其他 role 的后果。  
  不应要求任何候选提前猜出“延迟一分钟”或第二天“全部手动恢复”；应要求的是把具体后果及时呈现，让用户容易调整。

- **case-05：甲停止了未经确认的代码实施，却保留并强化了错误决策。**  
  甲 v0 派 Worker 改 clone 配置、做测试并提交推送；v1 不再这样做，这是实际的范围收缩。但它仍派 Worker 把笔记改成“不做换行符转换”，甚至称这句话为用户原话。用户原话反对的是 autocrlf 默认行为，无法支持这个更宽的禁令。  
  同时，甲面试3开始正确区分“额度恢复的决定”与“其他自动重试的推断”；面试1却仍称第4条与已确立原则直接冲突，两个输出之间不一致。TL 与 Worker 对3、4、5的调查高度重复。  
  乙从双角色调查改为只派 TL，并增加了两处有价值的辨别：调高阈值不能解决所有“无法保存”的内容；旧 HEAD 不足以证明工作树内容过时。这说明减少派活没有削弱技术判断。

- **case-06：甲不再因晚间而延期，但“一个决定”的计数不准确。**  
  甲 v1 保持修复和阅读的顺序，并明确不顺手扩修其他遗留项；它不再把可做事项机械留到明天。不过“是否把 Manager 提前、改成全局”包含优先级和角色作用域两个决定，用户可以分别同意或拒绝。  
  乙 v1 提出全局 Angela 与项目内角色不共享可能并存，是更有用的解释假设；它也保留了“不替用户采纳”的边界。  
  候选没有 issue 正文，因此不能要求它们直接给出后续被接受的精确路线，也不能把未识别全部转向含义算成读意图失败。

- **case-07：面试3改善明显，面试1仍容易调查过头。**  
  甲 v1 增加首份结果汇报点，明确测试重组、系统设置和 release 调优不能直接做；这能阻止原案例中的部分扩张。不过“三次左右”冷构建、每种配置2–3次测量仍可能很重，“每种配置”也没有总上限。面试1仍在要求完整基线后检查多个方向。  
  乙 v1 加入“不为找齐所有优化点延迟首份可执行结论”，但仍让 TL 与 Worker 重叠调查。Worker 又因“当前环境只读”仅交草稿：这应单独看作环境限制，不能把“没有执行优化”算成 v1 成功控制了范围，也不能未经核实认定是它虚构限制。  
  两者都更明确地保留了回到 M2 的顺序。

- **case-08：派活更经济，设计边界仍守住；甲增加了决策负担的风险。**  
  甲从两者同时参与、直接交接，改为 Worker 先写草稿，Manager 再决定交 TL 审查；也增加草稿完成即停的条件。代价是当前还没有草稿，却已经写了一份完整的后续审查 brief，并要求列出多个待决问题，弱化了 v0 的单一用户决定限制。  
  乙改为只派 TL，新增首个可用设计即汇报的条件。两者都没有把“是不是要开始实现”当成编码授权。  
  因而，这个案例没有显示 v1 已导致实现过度推进。甲“没有表示收尾，所以照常推进”的判断仍太绝对：背景中的“同一会话的末尾”可以支持更小的设计交付，但不支持强行延期到明天。

**3．哪些规则起了作用，哪些没有，哪些带来副作用**

**起作用最明显的是可直接约束动作的规则。**

“角色之间不直接交接”在四个 brief 案例中表现最一致：v1 均改为向 Manager 汇报。“默认只派一个”也有作用，尤其是乙的05、08，以及甲的08从同时派活改为分阶段派活。

“允许动作、交付物、停止条件”让 brief 更容易执行。07 的首份可用结果、08 的首份设计草稿，都是比“尽快汇报”更有效的边界。不过，只有面试3改善还不够；Manager 在面试1决定下一步时，同样需要一个停止点。

时间规则修正了甲在03、06、07中未经用户示意就延期的行为。08仍未进入实现，说明撤掉“深夜自动收尾”不必然导致失控。

**没有稳定起作用的是需要语义判断的规则。**

“推断标签不增加权限”没有阻止甲在05中制造文档决定。它遵守了“代码先不改”，却没把笔记中的“用户决定”视为同样需要依据的改动。

“选择最重要的另一种读法”没有解决04。甲知道关键后果，但未把它放在发布前；乙仍选择了恢复探测这个次要分歧。缺口在于按后果排序，并据此调整动作，而非多写一个 Alternative interpretation。

“一条消息最多一个决定”也未稳定执行。甲把多项推荐压成一句话，或称为“整体方向”，便当作一个决定；这只减少问号，没有减少用户需要判断的事项。

“保护势头”有局部反效果：03中，甲主动询问是否把观察正式做成功能，重新打开了本可略过的范围问题。

**副作用主要来自程序外显和规则冲突。**

- brief 更完整，但甲常重复背景、原话、推断、允许事项和完成条件；两角色接到相似任务时重复更重。
- “不派任务”也变成一份长 brief，或提前生成尚未触发的完整任务。
- “用户的理由比字面更重要……按理由行事”与“不用推断增加权限”之间缺少明确优先级。理由适合检查方案后果，不应自动成为改写明确指令的权限。
- “只有用户自己表示收尾时才收敛”消除了过强的时间判断，却把节奏判断变得过于二元。收敛交付规模与取消用户要求，应当分开处理。

材料没有精确字数统计，因此不宜声称 v1 总体增长了某个比例。能确认的是局部重复和新增决策，而不是所有回答都更长。面试1的固定字段本来就是题目要求，也不能把这些字段本身归因于 v1 的程序化。

**4．对 v2 的具体条文建议**

建议替换和压缩现有条文，而不是再追加一长串检查项。

1. **补强“原话、决定、推断”的边界。**

   > 引号内的用户原话必须逐字对应原消息。改写和概括标为你的理解，不标为原话。禁止把用户对某种机制的否定扩大为对整个类别的否定。记录到文档、记忆或 brief 的“用户决定”，与代码修改一样需要准确的授权依据。

   对05而言，能记录“用户反对照搬 autocrlf 默认行为”；不能记录“用户决定不做任何换行转换”。至于仓库约定，应保持未定，不要求提前猜中。

2. **替换“理由比字面更重要，不能达成时按理由行事”。**

   > 用用户给出的理由检查字面执行的实际后果。若两者有张力，先呈现一个具体后果和你的推荐，不自行改写明确指令。若分歧会改变权限、发布内容或产生已指出的风险，停在受影响的那一步；其余已授权工作继续。

   04最有价值的一句话是：“只停失败的 role 后，同域其他排队角色仍会在恢复时启动。”它比抽象讨论用户是否偏好手动恢复更容易引出纠正。

3. **合并“另一种读法”和行动风险检查。**

   > 只说一种会改变当前动作或误判代价最高的另一种读法；没有这样的分歧就省略。已经发现的关键风险必须体现在动作或停止点中，不能仅留在最终报告。用户提出观察时，先说明现有行为，不主动要求决定是否新增功能。

   这样既保留纠正入口，也避免03为了形式完整而重开功能讨论。

4. **重写插入任务的交付规则。**

   > 插入任务先完成用户点名的最小改动和必要验证，得到首个可用结果就汇报。其他方向先记录，不自动继续。测量优先使用已有数据；需要新测量时，限定首轮总预算，不只限定每种配置的次数。首报不得以穷尽优化点为前提。

   07应先交付符号配置和代表性体积、耗时结果，再决定是否值得继续调查。

5. **压缩派活规则，并减少重复任务。**

   > 默认只派一个角色。增加第二个角色时，说明它要提供第一份产出不能替代的证据或质疑。没有任务的角色只写一句“不派”及原因；后续任务等触发条件成立再写完整 brief。当前 brief 只保留执行所需的原话、目标、允许动作、交付物和停止点。

   这同时处理05的重复调查、08的预备任务，以及乙“没有任务也填满模板”的问题。

6. **按可独立选择的事项计算决定数。**

   > 一条消息最多要求用户作一个当前必须的决定。若用户能同意其中一项而拒绝另一项，它们就是不同决定，即使写在同一句话里。内部待决清单可以完整保留；面向用户只提出当前阻塞的一项，其余附在草稿中并明确无需现在回答。

   “Manager 是否全局”和“是否提前实现 Manager”不能仅因同属方向讨论而合成一个决定。

7. **调整时间与节奏规则。**

   > 时间是弱信号，不能据此取消或推迟用户明确要求的工作。结合用户措辞、当前工作阶段和会话收尾迹象，选择更小的交付步长。明确要求先设计时，交付设计即停；不要额外要求用户当场决定后续实现范围。

   这能保留03、07的推进，也让08自然停在设计，而无需猜测用户是否疲惫。

另可在“表达”中补一句：

> 上述步骤用于内部判断，不逐项复述给用户；优先交付具体结果、关键后果，以及必要的一项决定。

**5．这次对比能说明什么，不能说明什么**

这次材料支持三个结论：

- **v1 的操作性约束有局部效果。** 派活顺序、汇报对象、允许动作和停止条件，比 v0 更明确。

这次不能证明：
