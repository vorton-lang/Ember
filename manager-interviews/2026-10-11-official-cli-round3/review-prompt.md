# 审阅要求：Manager 指令初稿 v0 → v1 的前后对比

一个小规模实验：Lobotomy 的 Manager（Angela）用官方 CLI 运行，角色指令是一份初稿。上一轮用初稿 v0，这一轮用改过的 v1，题目和案例相同。你要判断：v0 下出现的几种失误，在 v1 下有没有消失；v1 有没有带来新的副作用。不比较哪个模型更好。

## 候选

- **甲**：同一个模型，两轮的推理强度相同。
- **乙**：另一个模型。上一轮推理强度为 high，这一轮为 xhigh。所以乙的变化不能全部归因于初稿。

不要猜测候选是哪个厂商的模型。

## 材料

- `manager-draft-v0.md`、`manager-draft-v1.md`：两版初稿。v1 是根据上一轮评审修改的。
- `cases/case-01.md` … `case-08.md`：历史、截断处的用户消息，以及只给评审者看的"之后实际发生了什么"和"选这个点的理由"。每个候选的输入开头都有一行运行时写入的用户本地时间（JST）。
- 回答：`v0/` 与 `v1/` 两组，文件名为 `iN-case-NN-{甲,乙}.md`。面试 1（推断用户状态）有 8 个案例；面试 3（写给 Tech Lead 和 Worker 的 brief）有 04、05、07、08 四个案例。

已知的案例问题，不要因此扣分：
- 多个案例的"真相"，是用户看到原助手的具体方案后才说出来的，在截断处推不出来（03、04、05 的换行部分）。这类案例看下一步能否以很低的代价引出同样的纠正。
- case-04 的真相不稳定。
- case-06 的候选看不到 issue 正文。
- case-08 的背景写着"同一会话的末尾"。

## 上一轮的失误（逐项核对）

1. **把推断升格为决定**：把推断写成用户原话、定案或"不再讨论"；或者凭推断让下层去落实（上一轮甲的 case-05：把反对 autocrlf 升级为"不做任何换行转换"，并派 Worker 落实）。
2. **行动违背自己列出的风险**（上一轮甲的 case-01、case-03）。
3. **插进来的小事扩大成开放式调查**，没有停止条件（case-07，面试 1 与面试 3；两个候选都有）。
4. **派活成本**：不必要地同时派 Tech Lead 和 Worker；让两者直接交接（上一轮乙常见）。
5. **深夜规则用力过猛**：用户没有表示收尾时，就开始收敛、推迟或取消用户要的事（上一轮甲的 case-03、06、07）。也看反方向：v1 只在用户表示收尾时收敛，会不会在 case-08 这类场景里推进过头。
6. **纠正入口的质量**：写出的"另一种读法"是不是那个会改变行动、或误判代价最高的（关键例子是 case-04：同一额度域的其他 role 恢复后仍会启动）。
7. **一条消息交给用户的决定数**：是否多于一个；待确认的事是否藏在报告里（case-04、case-08）。
8. **brief 是否写清允许的动作和停止条件**：这是 v1 新加的要求。
9. **读意图的能力有没有变差**：是否仍然利用了更早的历史，读出了话背后的约束。
10. **新的副作用**：篇幅变化；照着 v1 的程序逐条走，导致回答程序化、冗长；过度推进；其他。

## 输出（中文）

1. 总表：失误 1–10 × 甲、乙，每格写"改善 / 不变 / 变差 / 不适用"，再加一句依据（引用回答中的短句，标出案例和面试）。
2. 逐案简评：只写 v0 与 v1 之间有变化的地方。
3. v1 中哪些规则起了作用，哪些没有起作用，哪些带来了副作用。
4. 对 v2 的修改建议，具体到条文。
5. 这次对比能说明什么，不能说明什么。
