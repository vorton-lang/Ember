**Current goal:**
确定 Lobotomy 第一版的骨架设计。要定的点：一层多 harness 抽象，至少接 Claude Code 和 Codex；adapter 走订阅账号绑定的官方入口，不依赖 API；组织层用 MCP；所有 role 可替换；本地常驻进程加 GUI；第一版做完后用来管理 Lobotomy 自己的开发。

**Likely current state:**
用户逐条回答了助手的问题，也纠正了几处：

- "Manager 伪装成用户"不是问题，信封设计不需要了。
- 用户没有选定抽象方案。原话是"选择 ACP 还是自己写或者别的"，这仍是待定问题。

用户期待助手根据这些新约束修正设计，并给出抽象层的方案判断。

**Evidence:**
- "我们不能假设所有的服务都可以通过 api 提供"：接入官方 CLI，是为了用上各家订阅绑定的入口。
- "既然有两个 harness，那抽象是必须的，只是选择 ACP 还是自己写或者别的"
- "manager 就是它们的用户，不需要刻意绕过"
- "所有的 role 应该做成可替换的"；"永远在线这个暂时不考虑……暂时作为本地常驻进程"

**Alternative interpretation:**
"接入 harness"不一定排除 Agent SDK。SDK 底层也是拉起官方 CLI，可能沿用用户的登录。用户的真实约束可能是"必须用用户自己的订阅登录"，而不是"必须直接拉起 CLI 二进制"。两种读法会让 adapter 选出不同的形态，需要核实 SDK 在订阅登录下的行为和使用条款，不能凭推测定下来。

**What would be dangerous to assume:**
- 把 ACP 和自研抽象之间的取舍当作已经定了。
- 默认 Agent SDK 可以合规使用订阅登录。Lobotomy 是面向普通用户的产品，不是个人脚本，第三方产品使用订阅登录的条款风险更高。
- 把"暂时不考虑"的常驻在线、远程部署当成永久排除。
- 只用 Claude Code 的能力表来设计抽象，没有实际查过 Codex 提供哪些接口（`exec --json`、app-server、MCP server 模式等）。
- 继续保留已经被用户否掉的信封、反伪装设计。

**Next interaction strategy:**
