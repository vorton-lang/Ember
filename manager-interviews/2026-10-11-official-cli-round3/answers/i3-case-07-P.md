**Brief for Worker:**

**背景**

M2 第二部分（让运行时能启动 Claude）暂停，先做这件插入任务。做完汇报给我，不要自动接回 M2。

**用户原话（逐字）**

> "在此之前有个紧急任务，现在的检查已经有点慢了，需要优化精简一下，我能想到的有debug symbol不要开full，开line table，别的你检查一下，二进制体积也要看一下，target现在有快40GB了"

**用户明确说过的**

- 本地检查（编译、测试、clippy、前端测试）变慢了，要优化、精简。
- 调试信息从 full 改成只保留行号表（`debug = "line-tables-only"`）。
- 其他可以优化的地方，由你检查。
- 二进制体积要看。
- target 快到 40GB 了。

**我的推断（不是用户原话）**

- 用户最在意的是日常开发时跑一遍检查的耗时，其次是 target 的磁盘占用。
- "二进制体积"我理解为主要指 dev/test 产物：测试二进制带完整调试信息，是 target 膨胀的主要来源。另一种读法是 lobotomyd 发布版的体积。两种都测，但发布版只给数据和建议，不改。

**步骤**

1. **找到"检查"的实际入口**：仓库里的脚本或命令序列，加上前端测试。之后的计时都以它为准。
2. **记录基线（必须在清理之前做）**：
   - target 的总大小，以及按子目录分的大小（debug、deps、incremental 等），确认有没有多个 target 目录；
   - 一次增量检查的耗时：改动一个常改 crate（例如 core 或 harness）里的一行后重跑；
   - 主要测试二进制和 lobotomyd 的 dev 体积、release 体积。
3. **按用户的要求改**：workspace 的 dev profile 改为 `debug = "line-tables-only"`。
4. **找其他耗时和体积来源**：
   - 用 `cargo build --timings` 等方式看哪里慢；
   - 可以看的方向（只是线索，以实测为准）：
     - 依赖的调试信息能不能再降；
     - test、clippy、build 之间因为 feature 不一致导致依赖重复编译；
     - 集成测试二进制的数量；
     - incremental 的缓存占用；
     - 前端测试的配置；
     - Windows Defender 实时扫描 target 带来的开销。

**允许直接做**

- 修改 Cargo profile 和 `.cargo/config` 这类低风险、容易回退的配置。每项改动都要有实测收益。
- 记录基线之后，可以 `cargo clean` 或删除 target 里的过期产物。它只是构建缓存，而且改 profile 后本来就要全部重编。不要删 target 以外的任何东西。
- 本地检查全部通过后，提交并推送。改动分成独立提交，等 CI 变绿。

**不允许做，只写成提议交给我**

- 改 release profile（lto、strip、opt-level、codegen-units 等）。
- 安装或引入外部工具（sccache、nextest、lld 等）。
- 合并或重组测试 crate 这类涉及代码结构的改动。
- 修改系统设置，例如 Defender 排除项、Dev Drive。
- 降低测试覆盖：不许删测试、跳过测试，也不许缩减 clippy 检查项。
- 处理那个 Windows 上的偶发滚动测试失败。

**范围和停止条件**

- 从零全量重编最多跑三次左右：基线一次、最终一次，必要时中间一次。
- 增量计时每种配置跑 2–3 次，取中位数。
- 用户要求的那一项改完、测到有效数字后，即使其他方向还没探索完，也先汇报一次。

**交付和完成条件**

1. 前后对比表，包括：
   - target 大小；
   - 全量检查耗时；
   - 增量检查耗时；
   - 主要二进制体积（dev 和 release）。
2. 已应用的改动：每项的收益和提交号；本地检查和 CI 都已通过。
3. 提议清单：每项写预期收益（有实测更好）、代价或风险、需要用户做的决定。
4. 一句话说明哪些方向看过但没有收益。
5. 如果值得留存，在 notes 里简短记下 profile 的选择和理由。
