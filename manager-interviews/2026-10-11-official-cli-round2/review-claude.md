# Manager 面试第二轮盲审

评审范围：只读了 review-prompt.md 列出的文件（manager-jd.md、manager-draft.md、cases/case-01…08.md、answers/i1-*、answers/i3-*）。

用词：
- "原助手"指案例历史里的助手。候选回答里把它称为"执行者"。
- 总表里的"读出 / 部分 / 未读出"，指候选是否读出了用户意图，或者至少给了低代价的纠正入口。

## 2. 逐案简评

### case-01
- **X**：另一种读法是"订阅入口是接入约束，不一定意味着只能调用 CLI"，方向反了。危险项"把 SDK 等同于 API key"实际上在为 SDK 留门。计划"推荐先核实两家的订阅接入和会话控制能力，再据此比较 ACP 与自建接口"，违背初稿"不要先停下来调查"。这是诱人读法的完整形态。
- **Y**：从用户给的动机（"各类订阅会绑定专用入口"）推出"adapter 应该去驱动用户本机已登录的官方 CLI，而不是走 API key"。SDK 作为另一种读法，并准备对用户说一句"如果你接受 Claude 侧走 SDK……"。Y 还注意到用户把"Claude Code 接入为什么是硬性要求"答成了"GUI 是硬性要求"，并标为推测。
- **Z**：正确读法列出来了，但放在另一种读法里。计划"随后核实两家订阅入口与 SDK/CLI 能力"，仍把合规当成待查项。
- **真相**：可靠。但用户 2 小时后才明说"直接去调官方cli"。在截断处，只有 Y 的读法能让用户一句话确认。

### case-02
- 三者都没有把"转发原话"外推到向上。差别在向上的下一步：
  - X 只"保留为未决项"；
  - Z 给了接近真实的推荐；
  - Y 用一问附默认，内容就是用户后来说的"附件默认收起"。
- Y 还提出"原话应该由运行时按消息 ID 原样附上"。这与真实中被接受的机制一致，也符合用户"机械操作能搞定的尽量少用manager"的原话。

### case-03
- 三者都没有把这个发现当成功能需求。
- Y 点出了真实中决定这件事的依赖："这一 turn 的输出有没有进入 harness 的会话记录还没测过"。它建议"记一笔……不新增机制"，与真实结果（写进 ideas 和 harness-adapter，等实测）基本一致。Y 还指出"这个组合只在执行阶段有效"，用到了第 3 轮第 2 条。
- Y 的问题在时间。23:42 JST 时，它决定"第 4 轮明确留到明天"。用户实际一直推进到 00:36 以后。这是初稿深夜规则的副作用（见第 5 节）。
- X 写"已近午夜，不展开新一轮问题"。它收敛的是问题，不是用户要的工作，分寸更好。
- Z 没有用时间。这一次反而与用户的真实节奏一致。

### case-04
- **真相不稳定**：用户 6 分钟后改回"自动继续，延迟 1 分钟再试"；第二天又删掉全部额度自动恢复。
- 三者都按字面执行"按照正常失败处理"。三者都没有提出"延迟重试"这类中间方案，也没有直接点出理由（"不一定想要……立刻重试"）和字面（"先不要自动续"）不一致。
- **Y**：另一种读法"恢复后整个域都不自动调度新 turn"，以及计划里对用户说的那句话，在真实中正是引出用户改口的点。Y 还抓到"#4 已经按'自动继续'关闭，需要补一条更正评论"，并给出"七成左右"的把握。
- **X、Z**：另一种读法"连恢复探测也停"，恰好对上第二天的最终状态。这一点应该算它们的。X 还抓到"把'继续'仍限定为 interrupted，导致 failed 无法手动恢复"；Y、Z 也有这一点。
- **面试 3**：
  - Y 判断 Tech Lead "这次不派任务"，理由是改动小、已放行、本地 00:36。这是这一题最好的分工判断。
  - X、Z 都让 Tech Lead 先做一致性核对，再交给 Worker 发布。在收尾时段，这多了一道串行环节。
  - Y 的 Worker brief 把"继续"只放宽到额度失败的 turn，没有放宽普通 failed，与"按照正常失败处理"不完全一致。Y 把这一点标为推断，并要求在报告里指出缺口。

### case-05
- "可疑"的真实含义是质疑。三者都把"需要展开"读成先解释，但计划都要求给出改法。没有人去为原设计辩护。
- **Y**：三条推荐（挡下后先停住等用户、出错停下等手动重试、空闲消息前物化）与真实结果一致。Evidence 里写出"执行者只请用户看 3、4，用户自己加上了 5"。
- **Z**：写"不能写成所有自动重试都已被禁止"。用户在 04:09（"我们不该防御它"）和 04:45（"恢复统一由用户手动触发，减少维护面"）两次表达同一方向，并给出一般性理由。这时把它当成局部选择，是把初稿"局部选择不推广"用错了地方。
- **换行部分**：按已知问题不扣分，只看纠正代价。
  - X、Z 只在 brief 的边界里写"不添加换行转换"，可逆。
  - Y 让 Worker 把"已决定：不做换行符转换"写进笔记，还写了"不给 `.gitattributes` 做任何兼容处理或转换逻辑"。后者没有用户原话依据，也没有标为推断。它恰好与用户随后说的"换行跟着仓库走，不跟机器环境"相反。
- **Y 的 Worker brief 也有真实价值**：它要求核实槽位的 git clone 会不会继承全局或系统的 `core.autocrlf`。这正是原助手随后发现的问题。但它设计的实验是"全局开启 `core.autocrlf=true`……实验结束后恢复全局配置"，会在实验期间改动用户本机的全局配置。应该用隔离的配置做。
- **X、Z 的面试 3**：结构相同。Tech Lead 做分析；Worker 只读核查，结果直接交给 Tech Lead。问题都问得准。

### case-06
- 候选看不到 issue 正文，这里只看过程。
- 三者都没有把 issue 当成用户决定。三者都计划读完后给一个推荐，不逐条交给用户拍板。
- X 提醒不要"仍按旧路线直接断言 Manager 相关设计太早"。Z 提醒重新审视"#22 太早"。这两点都和后来真实的推荐（先做 Angela 的前置）方向一致。
- Y 在本地 22:01 就写"可以明天再做的事明确留到明天"。用户实际工作到次日 01:30。

### case-07
- 这一题的关键是不把点名的小事变成开放式调优。
- **面试 1**：
  - Z 最紧（"优先落实 line table"）；
  - X 次之（"最小改动"）；
  - Y 最宽（"而不是只改一行配置就交差"，要查链接器、feature 统一、前端测试）。
- **面试 3**：
  - Y 判断 Tech Lead 不派任务，这一点对。
  - 但 Y 的 Worker brief 列了 6 个排查方向，其中"检查脚本里是否有可以并行或去重的步骤"，正是真实中被用户叫停的那类工作。
  - Y 要求"改动已提交推送，CI 通过"之后才汇报。真实中用户等不及，在半小时后插话要结果；Y 的汇报会更晚。
  - X、Z 都没有时间盒，但都要求先汇报、不推送。这个顺序与真实一致：用户看完汇报才说"先推送"。
- Y 在面试 1 说"M2 第二部分明确留到明天"，在面试 3 又说"回报后回到 M2 第二部分"，前后不一致。用户的原话"在此之前"已经说明做完要回到主线。

### case-08
- 三者都读对了：先设计，今晚不实现，不发问卷。
- Y 指出原助手"在 host 目录下给她单独建一个库"的提议，本身就是用户担心的临时方案。这是全组最好的一处历史利用。
- Y 在面试 3 要求"如果要在 roadmap 里调整，标成'提议'"。这正好防住了真实中把"暂时这么设计"写成"用户确认"的问题。
- Y 的那一问（"是先出设计再定实现范围，还是要直接实现？"），用户原话"应该先做完多项目设计"已经回答了，多余。
- 分工：
  - X、Z 让 Worker 只读查代码，交给 Tech Lead。这等于给 Worker 一份 Tech Lead 自己也能做的填充任务。
  - Y 让 Worker 写设计稿，Tech Lead 找问题并审稿。这符合"Tech Lead 找问题，Worker 执行"的分工，但三段流水线在深夜偏重。

## 3. 画像

### X
- **擅长**：
  - 字面意图读得准，篇幅短。
  - 下一步通常不越权。
  - 深夜分寸好。它收敛的多是"不追加问题、不开新话题"；只在 08 把"详细设计留到明天"，而那一次用户自己也说了"太晚了"。
- **常错**：
  - 读不出字面下面的约束。01 把用户的动机当成可核实的条款问题；04 没看出理由与字面不一致。
  - 另一种读法写在分析栏里，很少放进给用户的那句话。
- **反复出现的失败模式**：
  - 面试 3 固定派两个角色，并让它们横向串联：04、07 是 Tech Lead → Worker，05、08 是 Worker → Tech Lead。
  - 没有一次判断某个角色这一轮不需要任务。

### Y
- **擅长**：
  - 利用更早的历史。05 把第 4 条接到"恢复统一由用户手动触发"；08 把 host 库提议接到"临时方案"。
  - 原话原样引用，并把原助手的记忆和用户原话分开（"这是执行者的总结，不是用户原话"）。
  - 给出把握度（"把握中等""七成左右""把握很大"）。
  - 每次最多一问，并附默认。
  - 能判断 Tech Lead 这一轮不需要任务（面试 3 的 04、07）。
  - 多次预见真实中随后出现的纠正点：02 的向上附件、04 的同域其他 role、05 的槽位 autocrlf、08 的"提议"标注。
- **常错**：
  - 深夜规则用过头（03、06、07），替用户决定"留到明天"。
  - 工程类 brief 范围偏大，没有时间盒（07）。
  - 偶尔把推断写成下层的禁止项或"已决定"（05）。
  - 没注意实验对用户环境的副作用（05 改全局 git 配置）。
- **反复出现的失败模式**：覆盖面求全。回答越长，事后命中真相的机会越多；在现场，也越可能把小事做大（07）。
- **篇幅**：X、Z 的 2–3 倍。

### Z
- **擅长**：
  - 篇幅短，范围控制最好（07）。
  - 有时把正确读法放进另一种读法（01）。
  - 面试 3 能把历史中的限制带给下层（08："不安装系统软件"）。
- **常错**：
  - 与 X 相同，读不出字面下面的约束。
  - 会把"局部选择不推广"用到用户已经重复表达的偏好上（05）。
- **反复出现的失败模式**：
  - 与 X 相同的面试 3 模板。
  - "用户明确说过 / 用户明确授权"下写的是改写，不是原话（04、07）。
- **注**：X 与 Z 多处措辞几乎一样。例如 08 的 Current goal，X 是"我理解为先完成多项目设计，再推进全局 Angela，避免她的数据和运行方式依赖临时方案"，Z 只多一个冒号；06 的 Current goal 也几乎同文。在这个样本里，两者分不出稳定的不同画像。

## 4. 结论

### 最合适：Y

依据：
1. Manager 的核心是读出字面下面的意图，并留下准确的纠正入口。面试 1 中，Y 在 01、04、05 明显更接近真实结果，在 02 与 Z 相当。01 中 X 没有给出 CLI 这条读法；Z 列了，但计划仍去核实条款。04 中 X、Z 都没有提同域其他 role 的问题。
2. 面试 3 中，Y 是唯一判断 Tech Lead 此时不需要任务的候选（04、07）。
3. Y 的原话纪律最好，与 case-02 定下的"原话由运行时原样插入、解读追加在后"最匹配。
4. 用户的立场是 Manager 只做需要判断的事，机械的事交给运行时。这偏向判断力强的一方，而不是便宜但机械的一方。

Y 需要的脚手架：
1. 改写深夜规则，不让它替用户决定"留到明天"；
2. 给绕路任务加时间盒：先交付点名项并汇报；
3. brief 里的禁止项也要标来源；
4. brief 不得要求下层改用户的全局配置；
5. 给用户的消息设篇幅上限。

### X、Z

- 适合意图明确、范围清楚的场景。篇幅短，深夜分寸好，范围控制好（Z 在 07 最好）。
- 主要缺口有两个：读不出字面下面的约束；面试 3 机械地派两个角色，并让它们横向串联。
- 需要的脚手架：
  1. 派任务前，逐个判断每个角色这一轮是否需要任务；
  2. 另一种读法必须写进给用户的消息；
  3. 原话由运行时插入。case-02 定下的机制本身就能补上它们改写原话的问题。
- 01、04 这类"从动机推出约束"的题，上面的脚手架补不上。

### 能否直接用作 Angela

- 三者都不能不加修改直接用。
- Y 加上第 5 节的修改后，可以进入自用和面试 5。
- X、Z 更适合作为备选或对照。
- 这个结论只基于面试 1 和面试 3。上行过滤（面试 2、4）还没有测，见第 6 节。

## 5. 指令初稿本身

### 起作用的，或至少三者都遵守的

- "用户已经放行的事，不再回问"：04 中三者都没有再要发布许可。
- "不给问卷或选项菜单"：没有候选发问卷。
- "区分事实、用户的决定和你的判断"：三者都用"用户明确说过 / 我的推断"分段。Y 做得最彻底。
- "一次局部的选择不推广成长期规则"：三者都写了类似的防护，例如 X 的"'先不要'也不等于永久否决"。
- 本轮材料里没有不带初稿的对照，所以不能断定这些行为是初稿带来的。

### 没起作用或有副作用的

1. **深夜规则过强。** Y 在本地 22:01、23:13、23:42 都替用户决定"留到明天"，而用户在这几个时间点都在继续推进。真实中属于收尾的只有 08（01:29，用户自己说"太晚了"）和 04（00:36，"你可以发布"）。
2. **"局部选择不推广"缺少判断标准。** Z 在 05 把用户两次表达、带一般性理由的偏好当成局部选择。
3. **"一句话写出另一种读法"只有 Y 用在给用户的话里。** X、Z 只写在分析栏。
4. **"不要先停下来调查"在 01 没拦住 X、Z。** 它们仍计划先核实条款再比较。
5. **初稿没有覆盖"是否派任务"。** X、Z 每次都派两个角色，并自行假定 Tech Lead 和 Worker 可以直接交接。
6. **初稿没有覆盖绕路任务的范围。** 07 中三者都没有时间盒。
7. **"简短"只约束了表达。** Y 的分析和 brief 都很长。这一轮无法判断它给用户的消息会不会也长。

### 建议的修改

以下都是建议，不是已定的规则。

- **深夜规则改为**："本地时间只是弱信号。用户说出收尾信号（例如'太晚了''今天最后一件'），或只给收尾性质的指令时，才收敛：只做必要的事，不开新话题，不加问题。用户在深夜仍在推进时，照常完成他要求的事，只是不主动开新话题。不替用户决定'留到明天'。"
- **长期偏好与局部选择的界线**："同一方向的偏好出现两次以上，或者用户给出一般性理由（例如'减少维护面'），按长期偏好对待。只出现一次、只针对一个具体对象的选择，不推广。"
- **派任务前先判断**："派任务前，逐个判断 Tech Lead 和 Worker 这一轮是否需要任务。小改动和已经放行的机械操作，直接交给 Worker 或运行时，不为它拉 Tech Lead 审查。不需要的角色，不派任务。"
- **绕路任务**："用户点名一个具体做法，再加一句'别的你看看'时，先交付点名的那项并汇报结果。其他方向列成候选，由用户决定是否继续，不展开成开放式优化。"
- **另一种读法的位置**：把"同时用一句话写出另一种读法"改为"在给用户的那条消息里，用一句话写出另一种读法"。
- **brief 的禁止项**："brief 里的'不允许'也要标来源。来自用户原话的，引用原话；来自你的推断的，写明是推断。"
- **环境副作用**："不要求下层修改用户的全局配置，例如 git 全局配置或系统设置。实验需要时，用隔离的配置。"
- **提问**：在"一次最多问一个问题"后补一句："用户原话已经回答的，不再作为问题提出。"

### 待决问题

Tech Lead 和 Worker 之间能否直接交接，还是一律经 Manager 或运行时？X、Z 默认可以直接交接。初稿和 JD 都没有写。这是设计问题，需要用户决定，这里不替用户补答案。

## 6. 这个样本能说明什么、不能说明什么

### 能说明的

- 在这 8 个回溯案例和这一位用户上，Y 在"从动机推出约束"和"留出准确的纠正入口"上稳定强于 X、Z。拉开差距的是 01、04、05；02、06、08 三者接近。
- 初稿里的几条底线规则（不回问、不发问卷、原话与推断分段），三者都遵守。它们能防止明显的失败，但区分不了候选。
- 深夜规则有可以观察到的副作用，值得修改。
- 面试 3 能测出"谁这一轮不该收到任务"。这一维和面试 1 的读意图能力不完全重合：Y 在 07 的面试 1 范围读得偏宽，在面试 3 却正确地没有派 Tech Lead。

### 不能说明的

- **只覆盖面试 1 和 3。** 上行过滤、打断判断（面试 2、4）和现场表现（面试 5）都没有测。JD §3.7 的"说不知道"，本轮没有能触发它的案例。
- **样本小。** 每个候选每题只有一次输出，看不出波动。8 个案例来自同一位用户的 3 个会话。
- **真相本身有问题。** 03、04、05 的部分真相在截断处推不出。04 的真相 6 分钟内反转，第二天又变。04 中 Y 的另一种读法对上了 6 分钟后的状态，X、Z 的另一种读法对上了第二天的状态。
- **事后偏差。** 评审者知道之后发生了什么。篇幅长的回答覆盖点多，事后更容易"对上"真相。它在现场会不会因此把小事做大，07 给了一个例子，但只有一个。
- **X 与 Z 高度相似。** 这个样本实际上只有两种画像，不足以检验 JD §7 的问题：这些维度能否稳定分离。
- **没有对照组。** 无法判断哪些行为来自初稿，哪些是候选本来就有的。要判断，需要用同样的案例，在不带初稿或只改动单条规则的条件下再跑一轮。
- **成本和时延没有比较。** 耗时注释按要求忽略了。
