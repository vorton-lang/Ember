# 官方 CLI 担任 Manager：第一轮面试（2026-10-11）

[Lobotomy](https://github.com/vorton-lang/Lobotomy) 的 M4 要实现一个全局的 Manager（Angela），默认用官方 CLI（Claude Code、Codex）运行。M4 之前，用 [Manager JD](../../notes/manager-jd.md) §5 的面试题小规模检验：官方 CLI 能否担任这个岗位。

这是第一次按 JD 的面试题跑真实材料。结论是弱证据，见"限制"。

## 条件

**候选**：A、B 是匿名标签，对应关系在 `answers/key.json`；每份回答的模型和耗时在同名的 `.meta.json`。

| 标签 | CLI | 模型 |
|---|---|---|
| A | Codex CLI 0.162.0-alpha.17.2 | 默认模型 gpt-6.1-sol |
| B | Claude Code 2.1.283 | 默认模型 claude-fable-5-1 |

**调用方式**（`interview.mjs`）：
- 每次调用都是独立的一次性运行，不保留会话：Claude 用 `-p --no-session-persistence`，Codex 用 `exec --ephemeral -s read-only`。
- 不加载用户配置，Claude 关掉文件与网络工具，工作目录是空目录。
- 提示词先说明 Manager 的职责，再给出案例的历史和截断处的用户消息。脚本中的 CLI 路径是运行时那台 Windows 机器上的。

**案例**（`cases/`）：
- 8 个决策点，由一个 agent 从 Lobotomy 的开发会话中抽取。这些会话发生在 2026-10-01 至 10-10，是用户与 Claude Code 之间的对话。
- 每个案例在用户的一条消息处截断。
- 发给候选的内容只有"历史"和"截断处的用户消息"。"来源"（含类别标签）、"之后实际发生了什么"和"选这个点的理由"三节，脚本在发送前去掉，只给评审者看。

**面试**：
- 面试 1（推断意图）：8 个案例。
- 面试 3（写给 Tech Lead 和 Worker 的 brief）：案例 04、05、07、08。
- 每个案例、每个候选只跑一次。

**评审**（`review.md`）：另一个 agent（Claude）评审。评审时它没有打开对应关系、`.meta.json` 和脚本。按 JD §7 写画像，不打分，不排名。

## 结果

两个候选在现状下都不能直接担任 Manager，失误的方向相反。

**A：分寸好，但被动。**
- 擅长：很少把推断说成事实，来源标注一致，授权边界写得清楚，篇幅短。
- 常错：
  - 很少调用更早的历史；
  - 对时间和收尾信号不敏感；
  - 该给推荐时，退回到"先调查"；
  - 指令明确时按字面执行。
- 失误多是遗漏。

**B：读人准，但行动偏离自己的分析。**
- 擅长：大量引用带时间的原话，常能读出指令背后的理由，注意时间和收尾；Tech Lead brief 中的质疑最具体。
- 常错：
  - 计划违背自己列出的风险；
  - 把推断升格为定论，偶尔写在"用户明说"下面；
  - 把多个决定推回给用户，例如注意到已是凌晨 1:30，仍然加问两件事。
- 失误多是做多了：多问、多查、多定。这正是 JD §3.3 点名的"脑补"。

**两者一起失误的案例**（04、05、06、07）：
- 多数案例的真相是用户看到原助手的具体方案后才改口，在截断处推不出来。
- 在这类案例中，能做到的最好行为是把关键假设摆出来，让用户有东西可以纠正。两个候选都没有做到。

**评审给出的补救方向**（未验证）：
- 运行时把用户原话插入 brief；
- 每轮输入带上用户本地时间，以及已定的决定；
- 只有用户原话能写"定案"；
- 输出前检查计划是否违背自己列出的风险；
- 给提问设预算，并要求给出一个推荐。

细节和逐案说明见 `review.md`。

**附带测量：每个 turn 的延迟**（`latency/summary.md`）：
- 官方 CLI 每个 turn 的固定开销约 1–2 秒，回复结束后进程还要约 1 秒才退出。
- 极短输入下的首段文字：Claude 约 3–4 秒（流式），Codex 约 4.5–5.5 秒（整条回复最后一次到达）。

## 限制

- 每个案例只跑一次，看不出方差。
- 8 个案例都来自同一个用户、同一个项目。
- 案例由 agent 挑选，偏向原助手出过错的点。
- 真相是用户对原助手具体回复的反应。候选给出不同回复时，用户可能走向别处。
- 候选看到的背景和历史经过选案 agent 的加工。JD 的面试 3 原本只给真实聊天内容。
- 只有一个评审者。它与候选 B 同属一个模型家族；回答的长短也会暴露候选的身份，所以匿名的效果有限。
- 没有做面试 2、4、5，没有测上行过滤和 live management。
- 案例本身的问题，例如 case-04 的真相不稳定、case-06 缺少关键输入，见 `review.md` §5。
