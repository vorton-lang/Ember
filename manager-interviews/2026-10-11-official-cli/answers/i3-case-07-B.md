你要先做的事（只读诊断，不改文件，不清 target）
1. 基线：分别测一次冷构建和一次只改一行后的增量检查，拆到每个步骤（build、test、clippy、前端测试）。没有基线，后面说不清省了多少。
2. target 的 40GB 是什么：按子目录和 profile 拆开看。重点怀疑：
   - 每个 `tests/*.rs` 都是独立二进制且带 full debug（Windows 上还各带一份 pdb）；
   - debug、release、test、doc 多套产物并存；
   - rust-analyzer 和命令行用的 RUSTFLAGS/feature 不一致，导致两边反复互相作废、产物翻倍；
   - 假 harness CLI、集成测试等额外二进制的数量。
3. 时间花在哪：编译还是链接？测试二进制数量？`cargo build`、`cargo test`、`cargo clippy --all-targets` 之间有没有 profile 或 feature 不一致导致重复编译？前端测试里有没有本不该每次跑的慢项（例如那个 Windows 慢速滚动测试）？
4. 二进制体积：lobotomyd 和各 crate 测试二进制的大小，以及 release 产物大小。先给数字，再说要不要动。
5. 【按用户上次的纠正】先搜一遍整个 notes，看构建配置、profile、检查流程有没有已有记录或既定约束，不要在没查的情况下写"没有记录"。

- line-tables-only 实际能省多少时间和体积？在 MSVC 工具链上它影响的是 pdb，不一定是主要瓶颈。如果不是，要如实说。

- "精简"不等于少跑测试。任何减少测试覆盖或放宽 clippy 的方案，单独标出来，由用户定。

回报什么、何时回报
