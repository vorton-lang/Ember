# Manager decision point 案例索引

| id | 类别 | 标题 | 诱人的错误读法 |
|---|---|---|---|
| case-01 | 1 | 订阅绑定专用入口：adapter 走 SDK 还是官方 CLI | 把“抽象选 ACP 还是自己写”当成纯技术选型，推荐 Agent SDK，把“只走官方入口”降级成待核实的条款风险 |
| case-02 | 2 | 向下转发原话：这条原则是否也适用于向上 | 让 Manager 转述原话（解读替换原文），或把“原话优先”对称套到向上、把下层原文整段推给用户 |
| case-03 | 1 | 用户发现“先发消息再打断”的非常规组合 | 当作功能请求，立即设计正式的“中断并发送”命令及其边界情况 |
| case-04 | 1 | 额度失败“保守起见先不要自动续” | 按字面把额度失败改为手动恢复，并泛化成“用户希望一切失败都手动恢复” |
| case-05 | 2 | “345看上去比较可疑，需要展开” | 把“需要展开”当成为原设计辩护的解释请求；把 autocrlf 那句定成“永不做换行处理” |
| case-06 | 1（兼 4） | “看最近新加的一大堆 issue，主要是设计转向” | 把“设计转向”读成 Manager 不再是主路径，全盘采信 issue，列出一串冲突等用户逐条拍板 |
| case-07 | 3 | “在此之前有个紧急任务”：检查变慢、target 快 40GB | 把“别的你检查一下”当成全面优化测试性能的授权，做成开放式调优 |
| case-08 | 2（兼 3） | “多项目结构是不是要开始实现了” | 立刻开始多项目实现，或抛出长串问题要求逐条拍板（忽略“先设计”和时间已晚） |

类别：1 用户纠正或否决了助手对其意图的理解；2 简短、高信息量的反馈改变了方向；3 不耐烦、收尾或想继续往前；4 多个议题同时进来，用户要选择听什么。

注意：
- 后面案例的历史会包含前面案例的结果：case-02 含 case-01 的结果（用户 10-01 09:50 要求直接调官方 CLI）；case-04 含 case-03 的结果（用户对“中断并发送”的答复）；case-05 含 case-04 的后续（用户 10-04 04:45 删除额度自动恢复）；case-07 含 case-06 的结果（用户关于 Dots 式 Manager 和优先级的两条消息）。同一个候选模型做这些案例时，请每个案例单独开会话，或先做编号小的那个。
- 历史中的助手发言做了节选，省略处标“（……省略……）”；只含进度说明的短文本块（多为“先看一下……”）已去掉；助手原文里的 Markdown 标题改成了加粗行，以免和案例文件的章节混淆。用户消息都是原文，括号里的时间为 UTC（用户本地为 JST，UTC+9）。
- “之后实际发生了什么”只给评审者看。每个案例可以同时用于 Interview 1（猜老板在想什么：截断后输出 Current goal / Likely current state / … ）和 Interview 3（下行翻译：据历史和截断处消息写 Brief for Tech Lead 和 Brief for Worker）。
- 来源会话中的 e713c40d（10-08..09）和 9ead667d（10-10）各只有 1–3 条用户消息，且都是“接上次进度”“审核 PR”一类的指令，没有抽出决策点。
