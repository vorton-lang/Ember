**第 1 轮：命令与占用的骨架**

1. **不再把 `admit / claim / finish` 当作 API。** 命令按领域命名，例如建任务、启动 turn、报告 `done`、验收。每条命令都写清五项：调用者与权限、前置条件、同一事务内写入的内容、幂等键、outbox 副作用。原来这三个词想表达的内容，这五项都已覆盖。
2. **占用分两层，每层一次取得。**
   - **任务层**：任务开始执行时，在同一个事务里占用 role 和它的槽位，直到任务完成或放弃。v1 里 role 和槽位一一固定，所以不会出现 #1 说的"拿到 role 却没拿到目录"。

3. **唯一约束由数据库强制**：
   - 每个 task 最多一个未关闭的 attempt；
   - 每个 role 最多被一个任务占用；
   - 每个 native session 最多一个未结束的 turn。登记中、运行中、unknown 都算未结束。
4. **一个 turn 就是一次 CLI 进程运行。** GUI 里的 Turn 直接用业务的 turn_id，不另起一套编号。
5. **MCP token 按 turn 发放。** 每个 turn 本来就要重新传 MCP 配置，所以没有额外成本；URL 不进 prompt，也不影响缓存。token 和发放它的 turn 永久对应。turn 结束后，如果旧进程还在调用，调用会被记为迟到，不能推进状态。

**1. 新进程不会继承上一个进程的配置**

**第 2 轮：turn 的生命周期与对账**

**1. turn 的状态**

| 状态 | 什么时候进入 |
|---|---|
| 已登记 | turn 记录、MCP token、绑定的输入消息在同一个事务中写入；CLI 还没启动 |
| 运行中 | CLI 已经启动。运行时记下 pid 和进程启动时间，用来避免 pid 被复用后认错进程 |
| 已结束 · completed | 收到 harness 的 turn 结束事件（Claude `result`，Codex `turn.completed`），而且 CLI 已退出 |
| 已结束 · failed | harness 报告了错误，例如额度被拒、登录失效、参数错误。这一类会触发系统故障通知 |
| 已结束 · interrupted | CLI 退出了，但没有 turn 结束事件。原因可能是停止或中断、CLI 崩溃，也可能来自对账 |
| unknown | 后端重启时，处于"已登记"或"运行中"的 turn 都改为 unknown |

completed 只说明这个 turn 正常结束了，不说明任务完成。任务完成要看 `done` 和验收。

**2. "待对账"只核对一件事：CLI 进程是否已经退出**

只核对这一件事就够了，原因有两个：
- `done` 等业务命令在发生时就已写入 SQLite，对话 item 也是完成时就落库，没有别的事实需要从 harness 那边补回来。
- 不恢复执行现场，所以也不用读 harness 的会话文件来重建什么。

核对方法：按记下的 pid 和启动时间检查。如果后端在记下 pid 之前就崩了，就按命令行里的 turn 标识查找进程。Codex 的 MCP URL 在命令行参数里；Claude 的 MCP 配置文件可以用 turn_id 命名。

核对结果分两种：
- **已退出**：turn 记为 interrupted，释放 native session 的运行权。接下来分两种情况：
  - 已经有 `done` 的采集意图：照常采集。
  - 没有：槽位保持原样，等用户选择继续、新建 native session 或放弃。
- **仍在运行**，例如 Linux 上 harness 没理会 SIGTERM：turn 保持 unknown，运行时定期检查它是否退出。GUI 显示"上一个 turn 的进程仍在运行"，提供"终止"按钮。运行时不自动杀进程。

**3. 消息的投递状态**

| 状态 | 判断依据 |
|---|---|
| 排队 | 在 role 的收件箱里，还没绑定到 turn |
| 已绑定 | 和 turn 登记在同一个事务里写入 |
| 已投递 | CLI 已启动，stdin 写入并关闭成功 |

投递之后，消息就跟随它所在 turn 的结果：completed / failed / interrupted / unknown。

"已处理"不做成机器状态。模型有没有真正照这条消息去做，属于语义判断；机器能确认的只有"投递它的 turn 是否正常结束"。输入有没有进入 harness 自己的会话记录要靠实测，这一项已在实验清单里。

**4. 未正常结束的 turn，它的输入消息不自动重投**

理由是"不重放"：resume 接的是原来的 native session，它的记录里可能已经有这条消息，自动重投可能重复。GUI 会把这些消息标成"所在 turn 未正常结束"，由用户决定继续还是重发。

**第 3 轮：M1 的任务流**

整理这一轮时我发现了一个之前没提过的问题，放在第 2 条。

**1. attempt 的边界**
- 每次进入执行阶段都开一个新的 attempt。进入执行的情况有四种：任务开始、验证失败、退回、重开。
- attempt 内每次运行 CLI 是一个 turn。同一个 attempt 里接着做，例如回答执行者的提问，只新建 turn，不新建 attempt。这一条是把 #7 的建议定下来。
- 执行者报告 `done` 或任务被放弃时，attempt 结束。之后的验证和验收，都针对这个 attempt 产出的候选成果。

**2. 新问题：离开执行阶段后，执行者还能不能跑 turn？**

`done` 之后，候选成果已经固定，任务进入验证和验收。如果这时用户给 Malkuth 发消息，它跑一个 turn 时可能又去改槽位。这样槽位就和候选成果不一致了：被审的是一份，目录里是另一份。下面第 3 条的重新物化还可能把这些改动冲掉。

我的建议：任务离开执行阶段后，发给执行者的消息先排队，等任务回到执行或关闭时再投递。代价是验收期间不能和 Malkuth 对话；想问它，就退回任务并附上问题。

**3. 回到执行时，槽位怎么处理**
- **默认保持原样**，执行者接着改。HEAD 仍是槽位物化时的集成版本，`git diff` 显示整个任务的改动。
- **例外**：如果验证时候选成果被 rebase 到了新的集成版本，就把槽位重新物化为 rebase 后的候选成果。有冲突时，冲突标记写进文件里；HEAD 设为新的集成版本。
  - 第 2 条保证了此时槽位内容就是候选成果，所以重新物化不会丢东西。
  - 这成为重新物化的第三种情况，也解决了 `harness-adapter` §6 里的那条未决项。
- v1 只有 Malkuth 一个 Worker，任务进行期间集成版本一般不会前进，所以这个例外很少出现。

**4. 修改完成条件**
- 用户随时可以改。每次修改生成一个新版本，不打断正在运行的 turn。
- 任务在执行阶段：运行时把新版本作为一条消息投递给执行者。
- 任务在验证或验收阶段：不自动退回。验收请求里带着完成条件版本（#7），版本对不上时验收会被拒绝，用户按新版本重新判断，再决定验收还是退回。
- 已经产生的证据仍然绑定旧版本。

**5. 证据什么时候作废**
- **检查结果**绑定成果内容、基线和检查配置，三者任一变化都要重跑。完成条件的文字变化不会让检查结果作废。
- **验收**必须针对当前的成果、当前的完成条件版本和当前的集成版本头（CAS）。
- **不会让证据作废的变化**：role 下线后再上线、换 native session、展示字段变化。
- **审查结论**绑定完成条件版本。基线变化后审查结论还能不能沿用，到 M2 再定。

**6. 重开**
- 只能重开已经关闭的任务，也就是已完成或已放弃的。重开会建立新的 attempt，然后进入排队。
- **代码起点**：把最后一份候选成果 rebase 到当前集成版本。没有候选成果，就从当前集成版本开始。对已完成的任务来说，这两种起点是一样的。
- **继承**：任务 ID、当前的完成条件版本、审查预算（已定，不重置）。
- **不继承**：检查结果、审查结论（已定）。
- native session 按 role 管理，重开时不换，轮换仍然手动。

attempt里有多个turn是什么一种场景

助手：[2026-10-03 14:35 UTC]
一个 turn 从 CLI 启动开始，到模型停下来不再调用工具为止。在一个 turn 里，模型可以连续调用几百次工具。如果 Malkuth 一口气把活干完并报告 `done`，这个 attempt 就只有一个 turn。

只要在 `done` 之前出现了新的输入，就会有第二个 turn。运行时不会在没有输入时自己启动 turn（manager-actions §6）。会产生新输入的情况有这几种：

1. **执行者自己先停下了。** 它问了一个问题（"用 A 还是 B？"），报告了阻塞，或者以为做完了却没调用 `done`。turn 正常结束（completed），任务还在执行阶段。用户回复之后，开始新的 turn。
2. **turn 进行中来了补充说明。** turn 跑着的时候不能插话（harness-adapter §1.1）。用户追加的说明，或者第 3 轮第 4 条的完成条件更新，会先进收件箱，等当前 turn 结束后作为下一个 turn 的输入。
3. **turn 被中断。** 用户停止、立即中断，或者后端崩溃。用户点"继续"后，经 resume 开始新的 turn。
4. **暂停后恢复，或额度恢复后接着做。**
5. **中途换了 native session。** 换完后的第一个 turn 在新 session 里跑，但仍属于同一个 attempt。

举一个例子：

```text
attempt 1
  turn 1  Malkuth 开始实现，中途问："检查命令用 cargo test 还是 nextest？"   → completed
  turn 2  用户回答 nextest，Malkuth 继续做，后端在这时崩溃                → interrupted
  turn 3  用户点"继续"，Malkuth 检查 cwd 后做完，报告 done                → completed
          → 采集候选成果，attempt 1 结束，进入验证
验证失败 → attempt 2
  turn 4  运行时把失败原因发给 Malkuth ……
```

两者分开，是因为管的事不同：
- **turn 是执行单位**：一个进程、一个 MCP token，对账也按 turn 做。
- **attempt 是业务单位**：一次执行最后交出一份候选成果，证据和验收都针对它。

如果把两者合成一个，那么问一个问题、或者崩溃一次，就得开一轮新的业务执行，证据和审查轮次也会跟着乱。
