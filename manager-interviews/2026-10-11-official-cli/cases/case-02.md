2. **放在仓库外面**：`%LOCALAPPDATA%\Lobotomy\worktrees\<repo>\slot-N`。放在仓库里的话，ripgrep、IDE 索引、测试运行器都会扫到这些嵌套副本。
3. **固定数量的槽位，循环使用。** 每个仓库 N 个槽位（N 等于最多同时写代码的 role 数，可配置）。
   - 分配给任务时：`git switch -C lobotomy/<task-id> <base>`。
   - 回收时：`git reset --hard` 加 `git clean -fd`。不加 `-x`，这样 `node_modules`、构建缓存这类被 ignore 的目录会保留，下一个任务可以直接用。
   - 磁盘占用的上限就是 N 份代码加依赖，从结构上不会越积越多。
4. **工作成果保存在 git ref 里，不留在目录里。** 回收槽位前，用 `git stash create` 给未提交的改动做快照，存到 `refs/lobotomy/snapshots/<task-id>/…`。之前提的"每轮快照、可撤销这一轮"也用同一套机制。分支和 ref 只占很少空间，到期后自动清理。所以目录可以放心回收，不会丢工作。

下面是同步合并方案。

**几个基本定义**

- **目标分支**：你主仓库当前检出的那个分支。两个槽位都从它分出来，也都合回它。
- **同步**：把槽位里的提交合进目标分支，并更新你的工作区，让改动直接出现在你的 IDE 里。只在本地进行，**不包括 push**。push 属于对外操作，单独约定。
- **同步的单位是 commit。** 角色指令里要求 Worker 每完成一个连贯的小步就提交。没提交的改动不同步，但会在 GUI 上显示，也有之前说的每轮快照兜底。

**同步流程**

同步由守护进程执行，不交给 agent：

```text
Worker 一轮结束，且有新提交
 ① 在 Worker 槽位里 rebase 到目标分支的最新提交
      有冲突 → 放弃这次 rebase，下一轮把冲突交给 Worker 解决
 ② 运行检查命令（按仓库配置，可选，比如类型检查 + 单元测试）
      失败 → 把输出发给 Worker
 ③ 在主仓库里执行 git merge --ff-only lobotomy/worker
      你本地有未提交的修改，且和要更新的文件重叠 → git 会拒绝
      → 标记为"被你的本地修改挡住"，之后重试
 ④ 记录一条同步事件（同步前后的 SHA），通知 Manager
```

**安全原则**

- **目标分支只做快进，永远不改写历史。** 需要改写的只有槽位自己的分支，那是私有的。
- **绝不碰你没提交的修改。** 这一点直接靠 git 自身的检查保证：会覆盖本地修改时，`--ff-only` 本来就会拒绝执行。
- **"撤销同步"用 `git revert`，不用 `reset`。** 你可能已经在同步进来的代码上继续工作了。
- **你自己在目标分支上的提交，下次 rebase 时自动带进槽位。** 如果你把主仓库切到了别的分支，同步暂停，由 Manager 提出来。

**TL 的槽位**

TL 的槽位用同一套机制，分支是 `lobotomy/tl`。每一轮开始前，如果它既没有未同步的提交、也没有未提交的改动，就移到目标分支的最新提交，保证 TL 审查的总是刚同步进来的最新代码。如果 TL 自己写了测试或实验代码并提交了，就走和 Worker 一样的同步流程。

**同步之前，你在 GUI 里看得到什么**

Workboard 上每个槽位显示：

- 领先 / 落后目标分支几个提交，以及有几个文件还没提交；
- 当前同步状态：已同步、检查中、有冲突（Worker 正在处理）、被你的本地修改挡住；
- 点开可以看 diff。

这样 worktree 里的工作就算还没同步过来，你也看得见。另外，Manager 可以暂停同步，比如方向正在重新讨论的时候。

**需要你定的两点**

1. **同步时自动更新你的工作区，可以接受吗？** 你在 IDE 里开着的文件会被改。我建议默认自动，因为这就是"尽早让你看到"的直接含义；你没提交的修改有 git 自身的检查兜底。另一种做法是攒着，等你点"拉取"再同步。
2. **每个提交都同步，还是 Worker 宣布一个阶段完成后才同步？** 我建议每个提交都同步，以检查是否通过作为门槛。检查命令没配置的仓库，就不经检查直接同步。

**用机制保证"原话"真的是原话**

Manager 不自己抄写原话，只给出用户消息的 ID，由运行时把原文原样插进去。这样 Manager 在结构上就改不了原话，也就不会出现"转述成了原话的样子"。这正好落实"机械的事归运行时"那条原则。

```text
send_to_role(
  role: "tl" | "worker",
  quote: [msg_id, ...],        // 用户消息 ID，可以多条，运行时按时间顺序原样插入
  context?: [msg_id],          // 可选：用户当时在回复的那条消息，也原样插入
  interpretation: string,      // Manager 的解读，追加在后面
)
```

下层实际收到的是这样：

```text
【用户原话】10-01 14:02
这个方向差不多，但是内存模型总觉得有点怪，先别大改。

【用户当时在回复】（Manager 10-01 13:58）
……

【Manager 解读】
……
```

`context` 是为了解决指代问题。用户说的"这个"，常常是指 Manager 刚转给他的某段内容，下层如果没看到那段，就不知道"这个"是什么。

**几条细则**

- **选哪些原话、发给谁，由 Manager 判断。** 不是每条用户消息都转给所有 role，闲聊和与该 role 无关的内容不发。
- **没有用户原话的消息，只有【Manager】这一段。** 比如 Manager 根据 Worker 的汇报主动追加的指令。标题由运行时固定生成，下层永远分得清哪些是用户说的，哪些是 Manager 说的。
- **解读用一个轻量模板，不做成严格的 schema。** 包括：我理解的目标、我推断的边界（能做什么、别做什么）、我不确定的地方、希望你什么时候回报什么。原话以外的内容都明确属于 Manager 的推断。
- **下层的角色指令里写明：原话优先。** 【用户原话】是用户本人说的；【Manager 解读】可能有错；两者冲突时以原话为准。

**需要你定的两点**

1. **解读和原话冲突时，要不要绕过 Manager 直接显示给你？** 我建议给下层一个专用工具 `flag_mismatch`，用来报告"Manager 的解读和原话对不上"。这类报告由运行时直接显示在 GUI 上，不经 Manager 过滤，因为这是在质疑 Manager 本身，不该由它决定你看不看得到。这条直达通道只用于这一种情况，不会变成下层随时找你的后门。
2. **向上方向要不要对称处理？** 也就是 Manager 把下层内容呈现给你时，同样"原文由运行时插入、Manager 的说明附在后面"；压缩成摘要的，你也总能在 GUI 里展开看原文。这对应 HCI 笔记里"让用户能质疑系统判断"的要求。如果你同意，向上方向就可以按同一套机制来设计。

## 选这个点的理由
这句话很短，却定下了 Manager 下行翻译的结构：原话不可替换，解读只是附注。好的 Manager 要准确传达“原话 + 追加解读”，同时不把它推广到用户没说的方向。诱人的错误读法有两个：让 Manager 转述或摘录原话，解读实际上替换了原文；或者把“原话优先”对称地套到向上方向，把下层原文整段推给用户。
