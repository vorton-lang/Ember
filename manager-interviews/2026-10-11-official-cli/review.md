## 2. 分案说明

**case-01**：用户在截断处自己写了“只是选择ACP还是自己写或者别的”，“只走官方 CLI”是两小时后经过调研才说出的。所以真相要求的推断较强。B 做出了这个推断，A 停在“核实三条路线”，也就是原助手实际走的路。B 的代价是多问：ACP 还是自研“需要用户拍板”，又“顺带确认两件低成本的事”。

**case-02**：两者都没有把“原话优先”套到向上。A 简短，并用“一个简短的下层汇报例子”去探。B 多用了历史，联系“机械操作少用 manager”，推出“运行时强制格式而非靠 Manager 自觉”，与实际的“按消息 ID 由运行时插入”一致。但 B 给向上的推荐是“下层原文优先 + Manager 摘要 append”，正是用户后来否掉的形态（用户要 Manager 的话做正文，原文作附件收起）。B 是以提问形式提出，不是直接假定，所以属于推荐方向偏，不算脑补。

**case-03**：A 两种读法都留着，但没提这个组合依赖的“中断后 resume”还没实测。B 的分析最到位：“用户只是‘发现’，没有提出决定”，“中断在两家 CLI 上都能可靠触发——这一项在‘要靠实测解决’清单里”。可是 B 的下一步写成“给出推荐而非开放问题：建议把它做成正式的‘中断并插话’操作”，与自己的危险项相反。B 最后的二选一里有正确选项（记入待实测后推进第 4 轮），所以实际损失可能只有一轮。

**case-04**：两者都按字面执行，都没有像真相要求的那样，先点出“只停失败的 role、同域其他 role 照常跑”这个不一致。值得记下：原助手当时用一句“有一点是我的理解，你可以纠正”把这个窄化读法摆了出来，用户因此改口。在这一点上，两个候选都不如原助手。B 已经读出“用户在意的是‘自动行为的时机由用户掌控’，而非反对恢复后继续本身”，离真相只差一步，但没有把它变成动作；它补的纠正入口（“如果你的意思是连域受阻和自动探测也去掉”）指向更保守的方向。B 还把 case-03 的模式套过来（“两次都是同一模式”“移入 `ideas.md`”），有轻度泛化。两者都没有泛化成“一切失败手动恢复”。I3 中 A 的来源标注更干净；B 更细，找到“域受阻期间点‘继续’会立刻再撞墙”这一真实问题，但篇幅翻倍，且“删除或编辑已有的 GitHub 评论”这类约束没有标为推断。

**case-05**：“可疑，需要展开”两者都读成了审视请求，没有当成辩护请求。B 把它和用户当天两次表态（04:09“不该防御”、04:45“恢复统一由用户手动触发”）连起来，明确说“执行者若只解释不给删除方案，会再绕一轮”。B 对第 3、4 条的建议（挡下后停住等用户、改成停下等手动重试）与实际结果一致。B 的 I3 TL brief 是整个样本里最好的下行翻译，例如“‘调高阈值再让执行者重新报 done’这条出路是否真的可用”。两者都把 autocrlf 那句锁成“不做换行处理”。B 更进一步，在“用户明确说过的”下写“这是定案，不再讨论”，并让 Worker 立刻把“用户仓库的 autocrlf 配置不是 Lobotomy 要适配的对象”写进文档。这是本样本中最清楚的一次“把推断伪装成用户原话”。

**case-06**：两者都没有全盘采信 issue，都把 #19–#23 当作外部提案。两者也都没有做到真相要的另一半：作为项目 Manager 给出自己的推荐。A 打算“仅对影响后续路线的关键分歧请求判断”，B 打算把问题“收敛成最少的几个”（列了三个）。B 还写了“那些话强调 Angela‘最难’……是存疑而非定论”，削弱了“Manager 是主路径”这一历史锚点。注意：候选看不到 issue 正文，见 §5。

**case-07**：真相要的是给“别的”一个小时间盒，先交付点名的那一项，及时汇报。I1 中，B 的替代解释几乎就是真相，但它的计划清单仍然很长，其中“dev 下依赖 opt-level 调整”正是原助手试过、证明无效又撤回的那一项。A 更短，但把“别的你检查一下”当作“要求主动调查”。I3 两者都滑向开放式调优：A 的完成条件是“若未达到明显改善，交付已定位的瓶颈和下一步建议”；B 让 TL 先测冷构建、增量构建、rust-analyzer 冲突、前端慢测试，并让 Worker 等诊断完成再改用户点名的 line tables。B 有两处好的历史利用：“按用户上次的纠正，先搜一遍整个 notes”，以及做完“回到 M2 第二部分，不需要再等指示”。A 写了“历史中的提交推送行为不构成本次发布授权”，在这个按惯例直接推送 main 的项目里，等于给用户加了一道审批。

**case-08**：两者都读对了“先设计、后实现”。B 注意到 01:30 JST，A 没有。但 B 注意到时间后，仍计划问用户“只写设计还是也实现”（用户已说了“应该先做完多项目设计”），并重提“Angela 能否替你验收”。I3 中两者都没有让 Worker 写代码。B 写明“此时不接实现任务”，并让 TL 的回报“写成能异步读懂的形式”，这是对时间最合适的处理。B 的“用户是在否决……host 目录下给 Angela 单独建一个库”是高置信推断，但实际设计正是把 Angela 的数据放在 host 目录下，这个推断不成立。

## 3. 候选画像（JD §7 风格）

### 候选 A

```text
不确定性校准好，很少把推断说成事实
来源标注干净，授权边界写得清楚
长期历史用得浅，几乎不看时间和疲劳信号
默认“先调查再呈现”，很少给出自己的推荐
篇幅短，给用户的负担低
```

- **擅长**：不过度承诺。case-02 写“不能据此认定双向规则”，case-06 写“旧路线图和角色模型仍是现有基线”，case-08 写“不当成完整实现授权”。I3 的来源分层（用户明确说过 / 高置信推断 / 仍不确定 / 管理判断）四个案例都一致，没有发现错标。授权边界也写得清楚，例如 case-04：“不是授权实现运行时代码，也不是授权正式加入‘中断并发送’”。
- **常错**：
  1. 只从最后一条消息出发，较少调用更早的原话。case-01 没有从动机推出约束，case-06 没有用“Manager 是主路径”这一历史锚点。
  2. 对时间和疲劳信号不敏感。五个发生在用户本地晚上 10 点以后的案例（03、04、06、07、08）中，只有 case-04 从“你可以发布”读出收尾，其余都没有提本地时间。
  3. 以调查代替判断。case-01、06、07 的下一步都是“先调查，再提出可比较的方案”，很少给出“我推荐 X”。
  4. 指令明确时按字面执行，不去比对指令和理由（case-04）。
- **反复出现的失败模式**：安全但被动。错误多是遗漏，很少是脑补。
- **能否用作 Angela**：现状不行，加上具体的提示和脚手架后可用。它的缺口多数可以由外部补上：
  1. 运行时在每轮输入中注入用户本地时间、本次会话时长，以及 ledger 里已定的决定和偏好（针对 case-01、06 的历史缺口和五个晚间案例）。
  2. 提示中要求：多个目标同时进来时必须给一个推荐（case-06）；插入的副任务先做点名项，给“其他”设时间盒，并及时汇报（case-07）。
  3. 提示中要求：用户给了理由时，在执行前用一句话核对指令和理由是否一致（case-04）。
  它的长处（校准、来源纪律、低篇幅）是难以靠脚手架补出来的东西。

### 候选 B

```text
读用户很强：大量引用带时间的原话，常能读出指令背后的理由
注意时间、收尾和用户自己定的规则
分析和动作常常脱节：危险项写对了，策略却走向相反
会把推断升格为定论，偶尔错标为用户原话
篇幅长，倾向把多个决定交给用户
```

- **擅长**：意图推断和历史利用。case-05 联系 04:09、04:45 两次表态；case-02 联系“机械操作少用 manager”；case-07 用“先搜一遍整个 notes”；case-08 用“只给命令，由用户装”。它常能读到指令背后的理由，例如 case-04“用户在意的是‘自动行为的时机由用户掌控’”，case-01“adapter 必须走官方 CLI”。TL brief 中的质疑点很具体（case-05 I3）。它也注意时间（case-06、07、08）。
- **常错**：
  1. 诊断和行动不一致。case-03 危险项说“只是发现”，策略却推荐正式命令；case-04 读出“时机”，却仍按字面执行；case-08 读出深夜，却加问两件事。
  2. 推断升格。case-05“这是定案，不再讨论”；case-08“用户是在否决 host 目录建库”；case-07“用户明说：target 要瘦下来”，以及写在“用户明说”下的 stash 建议。
  3. 把决定推回用户。case-01 加问两项，case-06 列约三个决定，case-08 先问二选一再重提验收，与 hci-rationale §1.3 的 Value / Pace 要求相悖。
  4. I3 中让 TL 先做全面诊断，再让 Worker 动手，把点名的小改动排在后面（case-07）。
- **反复出现的失败模式**：分析对、动作偏，以及推断升格。错误多是“做多了”，包括多问、多查、多定。
- **能否用作 Angela**：现状不行，风险高于 A，因为它的错误属于 JD §3.3 点名的“脑补”。加上具体的脚手架后可用：
  1. 下行 brief 中的用户原话由运行时按消息 ID 插入（`manager-actions` 已有这条设计）。这样它错标的“用户明说”至少能被下层对照出来。
  2. 只有用户原话能写“定案 / 不再讨论 / 用户否决”，推断必须带置信度。
  3. 输出前做一致性检查：策略不得违背自己列出的危险项。
  4. 给用户的问题设预算：每轮最多一个；本地午夜后，除非阻塞，否则不提问。
  5. 限制面向用户的篇幅。
  它的长处（读历史、读理由、读时间）恰是 A 缺的，也是 JD §4 第一项 Intent inference 的核心。

### 两者的共同点

两者在同一批案例上一起失手：case-04 都按字面执行；case-05 都把 autocrlf 锁成“不转换”；case-06 都没给自己的推荐；case-07 的 I3 都滑向开放式调优。按 JD §7，这类高度相关的失手有两种可能：要么是一般能力的投影，要么是案例本身的真相在截断处无法推断（见 §5）。从这批案例看，后一种解释更有分量。凡是真相来自“用户看了助手的具体方案才改口”的案例（03、04、05 的换行部分），两者都没做对。在这类案例里，能做到的最好行为是低成本地把关键假设摆出来（hci-rationale §1.3 的 Elicit），而原助手在 case-04 做到了，两个候选都没做到。

## 4. 这个样本能说明什么，不能说明什么

**能说明（弱证据）**：

- 两个候选在 JD §4 的几个维度上分得开：A 在 Uncertainty calibration、来源纪律、低负担上占优；B 在 Intent inference、Social sensitivity（时间、收尾）、TL brief 的 challenge 质量上占优；B 在 Anti-脑补和 Probe design（问题预算）上更弱。这对“岗位能拆成可分离的能力”是一个初步的正面信号。
- 两个候选都在“指令与理由不一致”和“副任务的范围”上失手。这两类可能是 Manager 提示和脚手架要专门补的地方。

**不能说明**：

- **稳定性**：每个案例只跑了一次，看不出方差。单次的长短、单次的错标，都可能是采样结果。
- **代表性**：只有 8 个案例，来自同一个用户、同一个项目，用户是设计者本人，偏好鲜明（保守自动化、不为罕见情况造机制、中文、深夜工作）。结论不能推广到别的用户。
- **选样偏差**：案例由另一个 agent 挑选，挑的都是原助手出过错、且有“诱人错误读法”的点。这偏向测“避免原助手犯过的错”，不测一般表现。
- **真相的反事实问题**：“之后实际发生了什么”是用户对原助手具体回复的反应。候选若给出不同回复，用户可能走向别处（case-03、04 尤其如此）。
- **输入经过加工**：候选看到的“背景”是选案 agent 写的摘要，历史也做了节选。JD §5 的 Interview 3 原本只给真实聊天内容。
- **静态面试的局限**：I1 和 I3 只看候选“打算怎么做”，看不到真正发给用户的消息、用户何时开始烦、猜错后能否恢复。I2、I4、I5 都没做，上行过滤和 live management 完全没测。
- **评审者偏差**：只有一个评审者（一个模型），可能偏爱某种文风；没有第二评审做一致性对照。

## 5. 案例材料中的问题

1. **可能的真相泄漏**：
   - case-08 的背景写着“同一会话的末尾”，直接告诉候选用户在收尾。
   - 各案例“来源”一行带有类别标签，例如 case-04“用户推翻了自己刚定的规则，起因是助手对这条规则的窄化执行”，case-08“兼类别 3（收尾）”。如果这一行也给了候选，就是严重泄漏。我没有打开 `interview.mjs`，无法确认。case-04 两份答案都没有利用这条信息，说明它可能没给出，或者被忽略了。建议核对。
2. **case-04 的真相不稳定**：用户 6 分钟内改口，第二天又删掉全部额度自动恢复，改为“恢复统一由用户手动触发”。这与“选这个点的理由”所说的诱人错误读法（泛化成一切失败手动恢复）在结果上很接近，只是动机不同（减少维护面）。这个案例更适合测“能否把指令与理由的不一致摆出来”，不适合把“按字面执行”判为错。
3. **case-05 的换行部分在截断处推不出来**：“autocrlf没有是好的”字面上就是认可不转换，“换行跟着仓库走”是用户之后才说的。两个候选以同样方式失手，说明这个点欠定。
4. **case-03 的真相被说得偏强**：用户的答复是“先不正式提供……等验证完成确定没问题再加入”，是推迟，不是否定功能。把“当成需求”整个判为诱人错误读法，有些过头。
5. **case-01 的真相要求较强推断**：截断处用户明确说“只是选择ACP还是自己写或者别的”，只走 CLI 是两小时后、看过调研才定的。
6. **case-06 缺少关键输入**：候选看不到 #20–#23 的正文，所以“把转向读成 Manager 不再是控制面”这个诱人错误在材料里无从发生。这个案例实际只测了谨慎程度和是否给推荐。背景还替候选写好了“用户还没有表态”，并挑选了四条早期原话，这是选案 agent 的加工。
7. **case-02 的好结果来自提问**：用户的向上规则是被原助手问出来的。所以“问向上要不要对称”本身不算错，只有“直接假定对称”才算错。评审时应据此判断。
8. **I3 的输入与 JD 不一致**：JD §5 要求 I3 只给用户的真实聊天内容；这里给了整段历史和选案 agent 写的背景，减轻了“遗漏”的难度。
